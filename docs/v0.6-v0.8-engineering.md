# Fusion, manoeuvre planning and validation

This milestone extends the v0.5 deterministic engineering simulator. Perfect ego localisation and geometric sensors remain explicit assumptions. These experiments do not establish real-world autonomous-driving safety.

## Baseline and boundaries

The preserved baseline is `200c240`, with 186 tests across 18 files. The baseline test suite passed before implementation (13.13 s Vitest wall time in the cloud workspace). Historical v0.5 measurements remain in `traffic-autonomy.md`; they are not measurements of the new estimator or planner.

The town has four 9 m two-way roads and one lane per direction. Its existing intersections cannot support a legal same-direction lane change. Manoeuvre experiments therefore use an explicitly modelled, separate multilane corridor. A corridor feasibility result does not imply that arbitrary town routes support overtaking.

## Data boundaries

Ground-truth polygons and scripted actor states belong to sensor generation, physical collision enforcement and validation. Online estimation associates measured geometry, without debug object IDs. Behaviour receives sensor observations and estimated tracks; map geometry and perfect ego localisation remain available. Validation may associate truth with estimates after the run to measure errors, but those matches must never feed control.

A tracked point is an observed object surface. It is not an inferred geometric centre or a complete occupied body. Covariance must include geometric observation uncertainty as well as numerical filter uncertainty. Missing radial velocity is unavailable data, not zero velocity. Missing measurements require prediction and ageing rather than repeated correction from a cached frame.

## Reproducibility and measurement limits

Physics advances in fixed 0.01 s steps; sensor acquisition uses simulation time. A repeated seeded configuration must reproduce recorded states. Recorded-state playback is distinct from re-running the controller: seeking selects a stored frame and must not advance the live Drive simulation.

Collision impact speed must be captured before contact enforcement zeros velocity. A metric that cannot be reconstructed from recorded data is reported as unavailable. Tracking comparisons must state the surface-versus-centre limitation; finite position RMSE alone does not prove covariance consistency. Scenario completion, no collision and no road departure are separate acceptance criteria.

Browser throughput and cloud wall-clock execution time are observations of that host. They do not predict Windows laptop FPS.

## Estimation and control integration

The constant-velocity filter estimates `[x, y, vx, vy]` and its 4×4 covariance. Continuous white acceleration drives prediction; scalar Joseph-form updates preserve covariance symmetry. Cartesian position observations use finite surface uncertainty. Radar adds a radial-velocity constraint, with ego sensor motion compensated; it does not supply an exact tangential velocity. Association uses a 2D Mahalanobis gate (9.21, the 99% chi-square threshold with two degrees of freedom), a 4 m geometric cap and one-to-one assignment within each acquisition.

Tracks confirm after three distinct acquisition timestamps, coast after 0.35 s without a measurement and expire after 1.5 s. Multiple modalities acquired at the same timestamp do not count as multiple temporal confirmations. Cached frames are consumed once. State and recording are bounded; the estimator keeps at most 128 tracks.

Fused control is an explicit simulation option (`fusedControl: true`) and is enabled by the validation runner. ACC accepts only confirmed, fresh tracks whose positional covariance trace is below 4 m². Tentative, stale or uncertain estimates fall back to raw observations. Raw LiDAR/radar/camera hazard checks remain active, so fusion cannot suppress an observed emergency. A stale primary LiDAR frame commands a degraded-mode stop even when predicted tracks remain available. The unchanged default control path preserves the v0.5 regression baseline.

Focused integration tests verify a measured fused-track lead distance of 6.4 m and relative speed of 2 m/s, fallback for uncertain/tentative tracks, emergency braking overriding requested acceleration, rejection of an adjacent-corridor false trigger, deterministic reset, sensor-dropout stopping, pause and manual takeover.

## Validation metrics and playback

The runner accepts seeded configurations, stationary directed-lane initial poses, destinations, radar noise, sensor dropout and time-gap settings. It advances without rendering, bounds runs to 120 s and batches to 12 entries, and stores acquisition-rate frames for recorded-state playback. Live control and physical acceptance checks still run every 0.01 s. Exported JSON, CSV and engineering reports describe recorded results; A/B comparison keeps configurations separate.

Truth polygons are recorded for validation only. Tracking position error is distance from an estimated surface point to the nearest truth polygon boundary, with one-to-one gated matching. It is neither body-centre error nor correspondence-level error. A covariance consistency statistic is therefore unavailable for polygon truth; a nearest-boundary residual cannot calibrate the filter covariance. Velocity comparisons use the matched actor's translational velocity and can include changes in the visible scattering surface.

Town clearance is computed from actual convex polygons at 0.1 s recording intervals. The reported minimum is a sampled minimum, not a guaranteed lower bound on clearance between samples. Collision and departure counters come from every fixed step. Acceleration metrics use physical velocity differences rather than stationary brake commands. No-contact runs have no impact-speed measurement; absence of AEB leaves response time unavailable instead of inventing a value. Blocked-route and dropout scenarios use safe-stop criteria separately from route completion.

## Planning scope and remaining work

The separate corridor defines four explicit 3.5 m lanes, including two eastbound lanes. Quintic candidates at 5/6/7 s are checked against inflated sampled body footprints, static polygons, destination limits, steering, acceleration and lateral acceleration. Dynamic envelopes use a simplified constant-velocity position/velocity covariance expansion with class-size margins; they are conservative fixture checks, not calibrated probabilistic collision guarantees. Feasible gaps must persist for 0.5 s; lane-change cooldown is 2 s. Candidates are rechecked every fixed step, with abort and safe-stop states. ACC/AEB still has priority. Significant, statistically qualified lateral track motion also enables crossing-conflict prediction; moving-away/parallel tracks have regression coverage.

Measured lane-change completion was 37.69 s (one transition), overtaking 37.75 s (out and return), and cut-in response 47.77 s (two transitions). A conservative estimate-induced stop can occur during passing. The blocked-corridor fixture stops rather than forcing a manoeuvre. Actual driving uses the existing bicycle integrator and collision checks; no lateral position correction is used.

Remaining limitations:

- The corridor is disconnected from the town and shown in engineering plots, not a new interactive 3D driving map. General town lane changes, intersection manoeuvres and dynamic map rerouting are not implemented; existing static-map rerouting remains available.
- Tracking is point/surface based: separate visible faces can yield duplicate tracks. It is not a full object-extent estimator. No calibrated covariance-consistency claim is made for surface-to-boundary matching.
- Actor behaviour is configurable through implemented presets; an arbitrary actor-script editor and configurable moving initial ego conditions in the validation runner remain future work. Radar noise is bounded deterministic noise, not Gaussian standard deviation; the existing noise parameter also affects radial velocity and bearing.
- Replay displays recorded trajectories/states, tracks and decision events. It does not rewind the live 3D scene or reconstruct complete raw sensor streams. Online behaviour never receives replay truth.
- Batch size is capped at 12 and recordings at 1,201 frames per result. The UI runs batches sequentially and yields between runs; a single headless run can temporarily occupy the browser thread.

## Verification and performance

Final checks: **236 tests across 23 files pass**, `npm run typecheck` passes, and `npm run build` passes (369.13 kB gzip JavaScript; existing large-chunk warning). The 186 original tests are unchanged. Browser checks exercised all four workspaces, normal/noisy scenario execution, replay seek/play/pause, A/B baseline retention, JSON/CSV downloads and the actual overtake experiment; no page errors were observed. The production reset/start-occupancy control regression also passed. Genuine screenshots: [Perception](screenshots/vector-v0.6-perception.png), [Planning](screenshots/vector-v0.7-planning.png), [Validation](screenshots/vector-v0.8-validation.png).

The final 15-run batch simulated 513.21 s in 30.62 s wall time (about 16.8× real time) on this cloud Linux host under concurrent test load. A tracker-only sample of 10,000 updates with 18 tracks averaged 0.079 ms/update, excluding sensor generation and rendering. The production JavaScript bundle is about 369 kB gzip and retains Vite's large-chunk warning. Browser verification used Chromium software WebGL; no Windows FPS benchmark was performed.

Recommended next milestone: validate an object-extent tracker with correspondence-aware uncertainty calibration, then connect explicit multilane geometry to the town and extend interactive manoeuvres with worker-based validation execution.
